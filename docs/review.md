## 1. Что есть что

**GSD-Core** (`@opengsd/gsd-core`, «Git. Ship. Done.») — крупный сторонний SDD-фреймворк: v1.7.0-rc.6, ~1500 файлов, `CONTEXT.md` на 240 КБ с сотней доменных модулей (dispatch pipeline, capability registry, gate predicates, worktree lifecycle и т.д.). Гонит агента через жёсткий цикл фаз **Discuss → Plan → Execute → Verify → Ship**, вынося тяжёлую работу в суб-агенты со свежим контекстом. Своя ценность — борьба с «context rot» и верификация того, что код реально работает.

**Superpowers** — вторая оркестрационная надстройка (SDD-процесс: spec → plan → волны исполнения → review + fix-wave). В вашем репозитории именно Superpowers управляет разработкой *самого стека* (`.superpowers/sdd/`, `docs/superpowers/`). Функционально её конвейер **дублирует** конвейер GSD — два независимых spec→plan→execute→review контура над одним кодом.

**Ваш слой `claude-config`** — надстройка поверх обоих: инсталлятор `setup.mjs` (962 строки), ~13 hooks, ~38 `.mjs`-скриптов, 16 env-переключателей, три механизма патчинга чужого кода GSD, форк-агент `gsd-executor-decomposing.md` (56 КБ), leanmode, stack-rules, graphify/Neo4j, token-usage, model-selection. Значительная часть — «клей» и компенсация чужих ограничений, а не бизнес-логика.

## 4. Разбор по критериям

### Время до MVP — CC:9 · SP:6 · GSD:3 · GSD+SP:2

Самый доказанный критерий. Голый агент собирал тестовый калькулятор за ~3 минуты; **полный конвейер GSD не уложился в 20 минут и был убит по SIGTERM — 3 раза из 3** (`PLAN.md`, `results.md`). Ваша же формулировка: «20 минут не хватает даже на старт полного конвейера для тривиального калькулятора», таймаут подняли до 180 минут, потому что «полный discuss→ui→plan→execute→verify конвейер действительно может занимать больше часа».

Superpowers легче GSD (один процесс spec→plan→waves), но всё равно добавляет фазу спецификации и планирования до первой строки кода. Связка GSD+SP — худшая: два конвейера планирования подряд.

Оговорка справедливости: на **большом** проекте «время до MVP» перестаёт быть релевантной метрикой — там ценится «время до *правильного* MVP без переделок», и фреймворки наверстывают. Но по критерию как он задан — голый CC вне конкуренции.

### Усложнение процесса — CC:9 · SP:6 · GSD:3 · GSD+SP:2

Голый CC: попросил — получил. GSD добавляет роадмап, `STATE.md`/`CONTEXT.md`, фазы, гейты, `.planning/config.json`, изолированные worktree, парк из 34 агентов `gsd-*`. Superpowers добавляет свой SDD-цикл. Связка — два независимых процесса поверх одного кода плюс места, где они конфликтуют (два механизма записи `.planning/config.json`: «whichever applies last wins on overlapping keys» — `gsd-defaults-and-statusline-design.md`).

Косвенное, но сильное свидетельство переусложнения — **сам факт существования leanmode**: отдельная система из хука + резолвера + 3 файлов правил + команды `/leanmode` + нового агента, построенная только чтобы *гасить* избыточность поведения по умолчанию. Инструмент-«гаситель» появляется тогда, когда базовый режим ощущается слишком тяжёлым.

### Оверинженеринг — CC:6 · SP:5 · GSD:3 · GSD+SP:2

Здесь два слоя: оверинженеринг *кода* и оверинженеринг *процесса*.

Голый CC получает 6, а не 9: без guardrails модель сама склонна к overengineering кода (именно против этого написан leanmode: «No speculative flexibility, no unrequested abstractions, no config knobs nobody asked for»). Но процессного оверинженеринга у голого CC нет.

GSD и связка теряют баллы на процессном оверинженеринге: STRIDE-реестры угроз, isolated-verification, capability-registry, gate-predicate-evaluator — мощно, но избыточно для большинства задач. Ваш слой добавляет свой: форк-агент **дублирует ~7000 слов** родного экзекьютора ради одного нового блока (`rules-src/gsd.md`: «duplicates the entirety of `gsd-executor.md`'s execution machinery … no inheritance mechanism»), `safe-statusLine`-гард реализован дважды независимо, два конфликтующих механизма дефолтов.

### Фиксы багов после MVP — CC:5 · SP:7 · GSD:7 · GSD+SP:5

**Единственный критерий, где фреймворки объективно лучше голого CC.** Весь смысл GSD — «nothing verifies that code actually works» решается verify-шагом, который «walks through what was built and generates fix plans before a phase is declared done». Superpowers даёт review-волну и fix-волну (`.superpowers/sdd/`: «10 code tasks + final review + fix wave all reviewed clean»). Меньше багов доезжает до продакшена → меньше времени на постфактум-фиксы.

Голый CC получает 5: индивидуальный фикс делается быстро, но багов в принципе больше (нет гейта верификации). Связка GSD+SP падает до 5, потому что каждый фикс приходится протаскивать через тяжёлую церемонию, и трение съедает выгоду от двойной верификации. Балл — суждение, эмпирикой по числу багов вы не мерили.

### Расход токенов — CC:9 · SP:5 · GSD:3 · GSD+SP:2

Доминирующий механизм перерасхода вы диагностировали сами (`_analize/context.md`): постоянная нагрузка **множится на (1 + N суб-агентов)**, потому что весь `CLAUDE.md` (~2710 токенов) + реестр скиллов заново выпускаются в каждом суб-агенте. Ваша таблица: 0 суб-агентов → ~3150 токенов, 5 суб-агентов → ~19 400 токенов только «постоянной» части, «`CLAUDE.md` перевыпускается 6 раз ≈ 16К токенов». GSD с его веером агентов и реестром из 69 скиллов (~1500 токенов) множит это сильнее всего; связка — ещё раз поверх.

Голый CC платит за контекст один раз. leanmode отыгрывает часть (~3–4× по токенам в удачных прогонах), поэтому ваш слой сдвигает GSD с 3 к ~4.

### Раздутие контекста — CC:9 · SP:5 · GSD:4 · GSD+SP:2

Близко к токенам, но с нюансом в пользу GSD. GSD **специально** держит главную сессию компактной, вынося тяжёлую работу в свежие суб-агенты — это уменьшает «context rot» в главном потоке (за это GSD получает 4, а не 3). Но *суммарный* контекст по всем агентам раздувается тем же множителем (1+N). Голый CC — самый компактный по умолчанию. Ваш `CLAUDE.md` (111 строк) + `gsd.md` (268 строк для GSD-проектов) грузятся статически в каждой сессии; session-init добавляет до ~10 динамических заметок.

## 5. Диагноз: откуда «в разы больше времени»

Три конкретных механизма, а не общее ощущение:

1. **Церемония до первого кода.** Discuss→Plan (GSD) и/или spec→plan (Superpowers) выполняются реальными суб-агентами по каждой фазе. На большом проекте это амортизируется; на маленьком вы платите час ритуала за 3 минуты работы. Прямое доказательство — таймаут-провалы сред 5/7.

2. **Множитель контекста (1+N).** Каждый суб-агент заново получает весь `CLAUDE.md` + реестр скиллов. Веерная оркестрация GSD/Superpowers плодит суб-агентов → линейный рост токенов и латентности на «постоянной» нагрузке, которая по идее должна быть бесплатной.

3. **Хрупкость оркестрации.** Ваш же бенчмарк RLM: вложенность агентов надёжна только до **глубины 2**; глубже — отказ или механический затык (`CONCLUSION-rlm-architecture.md`). Parallel-wave (цель 5×3 = 21 агент) **не достигнута ни разу**. Значит, время теряется не только на работу, но и на сбои/откаты/ретраи оркестрации, которые не видны в верхнеуровневых метриках (async-диспетчнутые агенты «не проявляются как Agent-события в родительском потоке»).

Плюс — стоимость *сопровождения*, которая не попадает в тайминг одной сессии, но крадёт ваше время: 18 из 19 рисков открыты и «accepted», патчи чужого кода привязаны к точным версиям и хешам и «ожидаемо отваливаются» после каждого `/gsd-update`, дрейф нумерации шагов чинился вручную в 9+ местах, собственные гейты (secrets-gate, fallow-nag) дают ложные срабатывания, которые приходится обходить руками.

## 6. Отдельная оценка: влияние вашего слоя `claude-config`

Вы просили это отдельно. Ваш слой действует в двух направлениях одновременно.

**Что он снижает (польза):**
- **leanmode** — режет `CLAUDE.md` на 18–28% (Tier A ~490 / Tier B ~760 токенов от 2710) и давит оверинженеринг кода у 6 «тяжёлых» агентов. При N=3 это ~2000–3000 сэкономленных токенов на сессию.
- **model-selection / gsd-defaults** — понижает модели дорогих агентов (opus→sonnet→haiku по 8 агентам), прямая экономия денег.
- **token-usage / graphify** — наблюдаемость и кросс-проектная память.

**Что он добавляет (стоимость):**
- **~150 КБ собственного кода/доков**, ~13 hooks, ~38 скриптов, 16 env-тумблеров — почти каждая фича со своим выключателем (сам по себе признак, что фич стало много).
- **Три механизма патчинга чужого кода GSD**, привязанных к версии+хешу: «a different version means the local file layout doesn't match». После каждого апдейта GSD патчи отваливаются — это не разовая настройка, а бесконечный цикл ре-синхронизации.
- **Форк-агент** `gsd-executor-decomposing.md` (56 КБ), 95% которого — скопированная механика родного экзекьютора из-за отсутствия наследования агентов. Дрейф отслеживается вручную (RISK-GSDEXEC-001).
- **19 рисков** (безопасность bootstrap RCE, утечки Neo4j-кредов, потеря требований при компиляции правил, скрейпинг цен без API и т.д.), 18 из них открыты.
- **Незавершённая консолидация**: два механизма дефолтов конфликтуют, «reconciling … is a separate, not-yet-scheduled task».

**Нетто-вердикт по слою.** На *живом* проекте, где всё уже установлено и стабильно, слой скорее **помогает** — экономит токены и деньги, даёт память и наблюдаемость. Но он же **добавляет постоянный налог на сопровождение** самого стека: вы тратите инженерное время не на продукт, а на удержание патчей в синхроне с чужими релизами. Проще говоря: слой лечит симптомы тяжести GSD (контекст, стоимость), но не её причину (церемония), и делает это ценой собственной хрупкости. Это **микро-оптимизация ценой макро-сложности** — большая инженерия ради экономии ~7 КБ автозагрузки, при этом добавляющая фоновые процессы и «принятые» гонки на каждой сессии.

## 7. Влияние leanmode (отдельный фактор)

**Что это.** Отдельная подсистема вашего слоя: хук `SubagentStart` впрыскивает YAGNI-правила («ленивый сеньор») в суб-агентов по типу агента. Четыре уровня — `off / lite / full / ultra` (`leanmode-rules.mjs`). `full` даёт лестницу «нужно ли это вообще → есть ли в кодбазе → в stdlib → в установленной зависимости → иначе минимум кода»; `ultra` добавляет активное удаление/инлайнинг и запрет новых файлов/зависимостей. Важно: режется **только сложность, не корректность** — «error handling at real boundaries, validation, and security practices stay in place regardless of level».

**Куда бьёт.** leanmode уменьшает **объём генерируемого кода** и его оверинженеринг. Он НЕ трогает статический множитель контекста (1+N) — ваш же `_analize/context.md` прямо говорит: «доминирующий множитель — не сам leanmode-инжект (40–162 ток), а перевыпуск всего `CLAUDE.md`». Сам инжект дешёвый; ценность — в том, что агент пишет меньше лишнего.

**Эмпирика.** В удачных прогонах `lean=full` дал ~4 400–4 800 токенов против 13 000–20 000 у `lean=off` — **в ~3–4 раза меньше** (`.test/results*.md`). Непостоянно: в одном из трёх прогонов вышло наоборот больше (шум). По умолчанию `full` включён у 6 «тяжёлых» агентов (executor, code-fixer, debugger, pattern-mapper, codebase-mapper, leanmode-executor); планировщики и security-аудиторы запинены на `off`, чтобы «не передушить».

**Где помогает больше.** Максимум пользы — там, где много исполнителей пишут код: GSD и связка. На голом CC с парой суб-агентов эффект мал.

| Раздутие контекста | 9 `(0)` | 5 `(0)` | 5 `(+1)` | 3 `(+1)` |
| **Сводная /10 (было)** | **8.0** (7.8) | **6.2** (5.7) | **5.0** (3.8) | **3.7** (2.5) |

**Вывод по leanmode.** Самая окупаемая ваша оптимизация: почти нулевая цена, а GSD тянет вверх на **+1.2** балла (3.8 → 5.0), связку — тоже на +1.2. Голый CC почти не двигается (+0.2), потому что там нечего «облегчать». Работает именно как компенсатор тяжести фреймворков — и это правильно, что он включён по умолчанию у исполнителей.

## 8. Влияние context-mode (отдельный фактор)

**Что это.** Базовый плагин (ставится отдельно, включён на USER-scope), который делает контекст-инжиниринг **на уровне инструментов**: жёстко запрещает `WebFetch` и маршрутизирует Bash / Grep / большие `Read` через свои `ctx_*` MCP-инструменты (`ctx_fetch_and_index`, `ctx_search`, `ctx_execute`, `ctx_batch_execute`, `ctx_execute_file`), чтобы **сырой вывод команд и файлов не попадал в окно контекста** — вместо него агент получает отфильтрованный/проиндексированный результат. Плюс метр контекста в статуслайне (`gsd-context-meter`) и диагностика `/ctx-doctor`. Ваш слой его дошивает: тихий tool-grant синк дописывает `ctx_*` во фронтматтер `gsd-*` агентов (только если плагин реально установлен), хардненинг `gsd-executor`/`gsd-debugger`, авто-апгрейд CLI.

**Куда бьёт.** context-mode уменьшает **входящий** контекст — то, что вливается в окно при чтении/поиске/фетче. Это ортогонально leanmode (тот режет **исходящий** код). Ни один из них не трогает третий рычаг — перевыпуск `CLAUDE.md` + реестра на каждого суб-агента; за это отвечает ваш план Tier A/B из `_analize`. Три рычага дополняют друг друга: context-mode = вход, leanmode = выход, Tier-trim = статика.

**Цена.** Плата не нулевая: (1) маршрутизация через `ctx_*` — лишняя дисциплина и иногда лишний round-trip (`ToolSearch select:<tool>` при deferred-схеме, индексация web-контента добавляет латентность); (2) ещё один сторонний плагин + CLI, которые надо держать в актуальном состоянии (авто-апгрейд — сам по себе поверхность риска); (3) сама секция CONTEXT-MODE в `CLAUDE.md` (~330 токенов) грузится каждую сессию (кандидат в lazy-skill по вашему же `optimizations.md`).

**Где помогает больше.** Максимум — на read-/search-/web-тяжёлой работе: ровно то, чем заняты research- и planning-суб-агенты GSD. На голом CC, где мало чтения, накладные расходы почти съедают выгоду.

Влияние по критериям (Δ к базовой матрице) и пересчёт:

| Критерий (10 = лучше) | CC | CC+SP | CC+GSD | CC+GSD+SP |
|---|:---:|:---:|:---:|:---:|
| Время до MVP | 8 `(−1)` | 6 `(0)` | 4 `(+1)` | 3 `(+1)` |
| Усложнение процесса | 8 `(−1)` | 5 `(−1)` | 2 `(−1)` | 1 `(−1)` |
| Оверинженеринг | 6 `(0)` | 5 `(0)` | 3 `(0)` | 2 `(0)` |
| Фиксы багов после MVP | 5 `(0)` | 7 `(0)` | 8 `(+1)` | 6 `(+1)` |
| Расход токенов | 10 `(+1)` | 6 `(+1)` | 5 `(+2)` | 4 `(+2)` |
| Раздутие контекста | 10 `(+1)` | 7 `(+2)` | 6 `(+2)` | 4 `(+2)` |
| **Сводная /10 (было)** | **7.8** (7.8) | **6.0** (5.7) | **4.7** (3.8) | **3.3** (2.5) |

**Вывод по context-mode.** Это единственный рычаг, который реально атакует **раздутие контекста** (leanmode его почти не трогает). На тяжёлых сценариях поднимает GSD на +0.9, связку на +0.8. На голом CC — по сумме **ноль**: накладные расходы маршрутизации ровно гасят выгоду, потому что б_а_зовому агенту нечего выносить из контекста. Вывод практический: context-mode стоит держать включённым в связке с GSD/волнами и не тащить на мелкие ad-hoc задачи.

## 9. Рекомендации

Отсортированы от самых окупаемых.

**1. Матчить инструмент под размер задачи — это главное.** Заведите явное правило: голый CC (или CC+leanmode) для всего, что делается за одну сессию; Superpowers-соло для средних фич с ревью; полный GSD — только для многофазных, многосессионных проектов, которые реально живут неделями. Ваша боль «в разы дольше» — это на 80% применение тяжёлого конвейера к лёгким задачам.

**2. Не включайте GSD и Superpowers одновременно на одном проекте.** Это два дублирующих spec→plan→execute→review контура (сводная 2.5 — худшая из всех). Выберите один процессный фреймворк на проект. Если нужен GSD — Superpowers пусть остаётся инструментом разработки *самого стека*, а не рабочих проектов.

**3. leanmode=full по умолчанию для исполнителей — оставить.** Это ваша самая дешёвая и работающая оптимизация (−3–4× токенов в удачных прогонах). Ваш выбор *не* включать агрессивный `standard`-профиль скиллов — правильный, лог `token-usage` подтверждает реальное использование урезаемых кластеров.

**4. Сократить `CLAUDE.md` по вашему же плану (Tier A/B).** Вынос graphify-CLI, context-mode, Model-Selection в lazy-skills даёт −18–28% на самой множимой нагрузке. INVARIANTS/SUDO/PRECEDENCE не трогать (нужны превентивно). Это вы уже спроектировали — доведите.

**5. Ограничить глубину оркестрации двойкой на уровне кода.** Ваш же вывод из RLM-бенчмарка: надёжно только «оркестратор глубины 2 + `Workflow` для всего глубже», без async/background-диспетчинга в headless-сессиях. Зафиксируйте это как жёсткое правило, а не как инструкцию в промпте.

**6. Сократить поверхность сопровождения слоя.** Форк-агент на 56 КБ, дублирующий 7000 слов, — кандидат на замену тонким патчем или на выпил, если изолированная верификация используется редко. Два механизма дефолтов — консолидировать (сейчас «not-yet-scheduled»). Каждый устранённый патч чужого кода = минус один вечный цикл ре-синхронизации.

**7. Домерить то, что не домерено.** Чистого числа «GSD в N раз дороже» у вас нет, потому что GSD-среды не дожили до финиша. Один аккуратный прогон *завершённого* GSD-конвейера против голого CC на средней (не тривиальной) задаче с таймаутом 180+ мин даст вам реальный множитель вместо оценок. Тогда решение «где порог включать GSD» станет основанным на данных.

- Полный GSD-конвейер: **3/3 провала по таймауту** на тривиальном калькуляторе; таймаут поднят 20 → 180 мин — `.test/PLAN.md`, `.test/results.md`.
